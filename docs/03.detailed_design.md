# 詳細設計書：ローカル完結型データ入力・一括印刷システム (PoC)

## 1. 目的

本書は、基本設計で定義した方針をもとに、PoC を破綻なく実装できる粒度まで処理・データ・責務を具体化する。  
ただし、実装コードそのものや細かなクラス名・関数名は定義しない。

---

## 2. 実装前提

- 言語: Python
- Web フレームワーク: FastAPI
- 画面: HTML + JavaScript
- 保存形式: JSON
- 帳票生成: Excel テンプレートを利用
- 動作環境: ローカル Windows PC を想定

PoC のため、認証・権限・監査ログなどの運用機能は実装しない。  
一方で、将来追加しやすいようにデータの入出力境界は分離する。

---

## 3. 論理構成

### 3.1. UI 層
画面入力、候補選択、メッセージ表示、一覧更新を担当する。

### 3.2. API 層
画面からの保存・取得・確定要求を受け、入力検証と業務呼び出しの窓口になる。

### 3.3. 業務ロジック層
以下を担当する。
- 入力値の正規化
- 日付/時刻形式の確認
- 同日同一社員の重複判定
- 保存データの整形
- Excel 出力対象の確定

### 3.4. I/O 層
以下を担当する。
- roster.json の読み込み
- 日別 JSON ファイルの読み書き
- Excel テンプレートの複製と書き込み
- 既存 Excel のバックアップ

この分離により、将来保存先を SharePoint などへ変更する場合も、UI と業務ルールの変更範囲を抑えられる。

---

## 4. データ詳細

### 4.1. 保存レコード
1 件の保存レコードは次の属性を持つ。

- date: 日付
- employee_number: 社員番号
- employee_name: 氏名
- start_time: 開始時刻
- end_time: 終了時刻
- reason: 理由
- remarks: 備考

#### データ型の考え方
- date は文字列で保持する
- 時刻は HH:MM の文字列で保持する
- 数値化は行わない
- 空欄を許容する項目は空文字で保持する

### 4.2. 名簿レコード
名簿は次の属性を持つ。

- employee_number: 社員番号
- employee_name: 氏名

### 4.3. 日別保存単位
保存ファイルは日付単位で分割する。

- 保存先: data/YYYY-MM-DD.json
- 内容: その日付に紐づくレコード配列

日付ごとにファイルを分けることで、検索範囲を狭め、翌日初回入力時の初期化判定を簡単にする。

## 5. 画面詳細

### 5.1. 初期表示
画面表示時に以下を設定する。
- 日付: 当日
- 開始時刻: 現在時刻
- 終了時刻: 空欄
- 氏名候補: roster.json の一覧を表示
- メッセージ: 空欄
- 一覧: 選択中の日付に紐づく保存データを表示

### 5.2. 入力項目の役割
- 日付: 対象日の切替
- 氏名: 入力主体
- 社員番号: 氏名連動または直接編集
- 理由: 任意説明
- 開始時刻: 必須に近い運用値だが、PoC では空欄や不完全値は検証時に確認
- 終了時刻: 任意
- 備考: 任意

### 5.3. 候補選択
名簿は入力欄の自動サジェストではなく、候補一覧として表示する。  
候補から氏名を選択した場合のみ社員番号を連動させる。  
候補にない氏名は自由入力を許可する。

### 5.4. メッセージ表示
成功・失敗メッセージは画面上に 1 箇所で表示する。  
表示位置は、入力フォーム、一覧表、Excel 生成ボタンの下を基本とする。

---

## 6. 保存処理詳細

### 6.1. 受付内容
保存要求は画面上の入力値をそのまま受ける。  
サーバー側で以下を確認する。
- 日付が存在する
- 氏名が存在する
- 日付形式が YYYY-MM-DD である
- 時刻形式が HH:MM であること（入力がある場合）

### 6.2. 正規化
保存前に次を行う。
- 前後空白の除去
- 空欄の統一
- 重複判定用キーの整形

### 6.3. 重複判定
同日同一社員の判定キーは次の優先順とする。
1. 社員番号
2. 氏名

同日内で既存キーが一致した場合は、既存レコードを新しい入力値で置換する。  
一致しない場合は配列末尾へ追加する。

### 6.4. 保存結果
保存成功時は、保存したレコードと成功メッセージを返す。  
保存失敗時は、失敗理由をそのまま利用者へ表示できる形で返す。

### 6.5. 画面更新
保存成功後は、対象日付の一覧を再取得して最新状態を反映する。

---

## 7. 一覧取得詳細

### 7.1. 取得条件
対象日付が指定された場合は、その日付のレコードのみ返す。  
日付指定がない場合は全件返す。

### 7.2. 表示列
一覧には以下を表示する。
- 日付
- 社員番号
- 氏名
- 理由
- 開始時刻
- 終了時刻
- 備考

### 7.3. 空データ時の扱い
該当データがない場合は、空状態メッセージを表示する。

---

## 8. 確定処理詳細

### 8.1. 対象
確定は、画面で選択中の日付を対象とする。  
入力中の日付がそのまま出力対象になる。

### 8.2. 出力手順
1. 対象日付の保存データを取得する
2. 既存の出力ファイルがあるか確認する
3. ある場合は backup 配下に退避する
4. template/template.xlsx を元に出力ファイルを生成する
5. 一覧データを所定列順で書き込む
6. 保存して完了とする

### 8.3. 出力レイアウト
出力ファイルは既存テンプレートの見た目を優先する。  
現行テンプレートでは `Print` シートが印刷シート、`Data` シートがデータシートであり、印刷シートの数式と書式を変更しない。
データシート側には以下の順序で値を配置する。
1. 日付
2. 社員番号
3. 氏名
4. 開始時刻
5. 終了時刻
6. 理由
7. 備考

### 8.4. 再出力
確定後も JSON を残すため、同じ日付で再度出力できる。  
ただし履歴の差分比較や復元機能は持たない。

---

## 9. バックアップ詳細

### 9.1. 対象
既存の Excel 出力ファイルがある場合のみバックアップする。

### 9.2. 保存先
- backup/ 配下
- ファイル名は日付付きで保持する

### 9.3. 失敗時の扱い
バックアップに失敗した場合は、既存ファイルの上書きを避ける。  
利用者には出力失敗として通知する。

---

## 10. エラー設計

### 10.1. 入力エラー
- 日付なし: 400 系相当の入力エラー
- 氏名なし: 400 系相当の入力エラー
- 日付形式不正: 400 系相当の入力エラー
- 時刻形式不正: 400 系相当の入力エラー

### 10.2. データファイルエラー
- JSON が読めない: 空データ扱いではなく、保存時に上書きできる状態を優先
- 保存失敗: 画面メッセージへ反映
- 出力失敗: 画面メッセージへ反映

### 10.3. UI 表示
エラーは画面上のメッセージ領域へ集約し、利用者が次の操作に移れるようにする。

## 12. 実装時の判断基準

- 画面で完結する操作を優先する
- 追加ライブラリは最小限にする
- 業務ロジックは保存・一覧・確定の 3 つに分けて考える
- データの責務を UI に押し付けない
- 将来の保存先変更に備えて、ファイル入出力は集約する
